BEHIND THE CURTAIN

FROM MOD MANAGER TO A MODDING FAMILY

Limelight did not begin with a plan for runtime model swapping, online co-op or restoring arena creation. Each part of the family grew from one question: what if I could make this work too?

5 early development videos
3 highly scientific drawings
1 increasingly questionable family

It Started as a Mod Manager

Limelight began with a much smaller purpose: make modding Dead as Disco easier. Installing replacement archives by hand meant moving package files around, remembering what was enabled and untangling everything again when something went wrong.

The original app brought imports, mod organisation, profiles, launch modes and compatibility checks into one place. At this point Limelight lived almost entirely outside the game. It could prepare the stage, but once Unreal was running it could not change the performance.

Crossing into the Running Game

A desktop mod manager can copy files and launch a game, but it cannot safely tell a live Unreal character to replace its mesh. That gap led to the native bridge: the part of Limelight that works inside the running game while the app remains outside as the organiser and interface.

UE4SS provided the runtime foundation. Lua handled session coordination and the native C++ bridge exposed the focused operations Limelight needed. Together they created a route from a button in the app to a real object inside Dead as Disco.

WHY A BRIDGE?

Limelight decides what should happen. The bridge performs the Unreal-specific work where the game can see it. Keeping those responsibilities apart let the interface grow without burying low-level runtime behaviour inside the app.

What began as an experimental connection gradually gained startup discovery, health checks, level-change locks, package-cache handling and safer recovery. That bridge became the foundation for everything that followed.

15 JULY 2026

The First Live Model Swap

The first successful hotswap was not polished, but it answered the important question. A replacement model could be changed while the game was still running. There was no return to desktop and no full restart between mods.

15 JULY 2026

The first model swap performed while Dead as Disco remained open, proving the core Live Loader idea could work.

Into the interface on the same day

A technical demonstration was only the beginning. Later that day I wired the experiment into Limelight, turning a development command into the first model swap controlled through the app's interface.

15 JULY 2026

The first replacement selected and applied through Limelight rather than triggered directly through development tooling.

Turning the Trick into a Live Loader

Making a model appear once was not the same as making live switching dependable. Early repeated swaps could leave models completely black because changing the skeletal mesh alone did not correctly refresh its materials, textures and cached packages.

A later game update also moved the mesh that mattered. The old SK_Charlie target remained on the main menu while gameplay used a different active mesh. The loader had to stop assuming one fixed object and find the character that was actually performing in the current level.

Solving those failures shaped the regular Live Loader: inspect the mod, identify its target, mount the new containers, release stale package state, refresh the live mesh and its materials, then report success or a useful error back to Limelight.

Support also grew beyond one kind of package. CRM and CSL replacements could take part in the same workflow, while improved inspection began identifying Charlie, Arora, Hemlock, Bouncer, Prophet, Dex and other targets instead of treating every replacement as Charlie.

18 JULY 2026

X19 Takes Live Switching Off the Desktop

X19 was developed only after the regular Live Loader had been hammered into something solid. The goal was not to replace that workflow, but to make repeated switching feel immediate during play.

Instead of returning to Limelight for every change, X19 lets a player rotate through an ordered or shuffled group using a simple keyboard keybind or controller button.

18 JULY 2026

The first trial of X19's keybind and controller driven switching, built on the now-reliable regular Live Loader.

The LimelightMP Journey

“Is it possible? Am I capable?”

I INTENDED TO ANSWER BOTH.
14 AUGUST 2026

The local co-op session that sparked it

The first successful local co-op session was played entirely by me. I controlled one character with a controller and the other with keyboard and mouse. It was awkward, but it proved the game's real couch co-op framework was there to build upon.

If both local players could already exist in one session, perhaps the second set of inputs did not have to come from the same desk. That thought became the framework idea for LimelightMP.

14 AUGUST 2026

One person, one controller, one keyboard and mouse, and the local co-op experiment that sparked the structure of LimelightMP.

16 AUGUST 2026

The first “online” game

The first online experiment sent my inputs to a friend's PC while I watched their split-screen game through Discord. It technically worked, which was exciting, but the problems were impossible to ignore.

  • Input had to travel to the host before the game could react.
  • The returning Discord video added another layer of delay.
  • I watched the host's split screen instead of rendering my own view.
  • Only the host needed to run a copy of the game.

It proved that remote input was possible, but it did not feel like two people truly playing together. I felt I could do better.

16 AUGUST 2026

Inputs travelled to a friend's PC while the returning split-screen view came through Discord: online in the loosest possible sense.

From a Stream to Two Local Games

LimelightMP changed the experiment so both players run and render their own copy of Dead as Disco. The host owns the authoritative vanilla couch co-op world. The client sends authenticated input over the private Tailscale route, and the host's controller bridge applies it to player two: Chuckles.

Unreal replicates the host-owned world back to the client, which draws its own view with a local camera. No Discord gameplay stream is required. The same willingness to cross from Limelight into the running game for Live Loader now carries a remote friend's input into a real local co-op slot.

Is it possible?

The working host, client, relay and native controller bridge answered yes.

Am I capable?

Every broken first attempt, repaired material and questionable drawing answered that too.

THE JOURNEY IS NOT FINISHED

LimelightMP remains experimental. Level changes, cameras, dialogue, rhythm synchronisation, audio, player-local menus and replicated effects still need work. This page records progress, not a claim that the final destination has been reached.

22 AUGUST 2026

Arena Modding Was Broken, So ArenaKit Joined the Family

Arena modding stopped working in Dead as Disco, so we brought it back.

LIMELIGHT ARENAKIT

Custom arenas had worked before, but the old route had quietly fallen apart as the game and Unreal changed underneath it. The remaining guide described an older setup, old starter packages now crashed and nobody had a current SDK or maintained editor project to fall back on.

The investigation began with whatever the community still had: the outdated guide, current cooked game packages, an older cooked arena known to have worked on 6 May 2026 and a lot of crash reports. FModel made it possible to inspect package properties and confirm that static mesh components, volumes and other level data had changed, but it could not turn cooked content back into the project that originally created it.

COOKED IS NOT EDITABLE

A .pak can preserve enough for the game to load an arena, but cooking strips away a lot of the editor information. The real breakthrough needed an older editable .uproject, not just another extracted .umap.

The first replacement map was deliberately simple: a floor, walls, lighting and a player start. It loaded instead of crashing. The HUD appeared, the player spawned and the game entered the arena route correctly. It looked like a giant smoke test because that is exactly what it was.

The map loaded

The replacement path, Unreal version and container packaging were finally correct.

No enemies spawned

Loading was only half the problem. Collision, reachable navigation and current gameplay volumes still had to be rebuilt.

That blank arena answered the packaging question but exposed the gameplay one. Dead as Disco chooses enemy positions from reachable navigation. Without a working floor, NavMesh bounds and safe spawn space, a level can load perfectly and still remain completely empty.

A preserved editable arena project finally supplied the missing comparison. Once its outdated references and components were carried into the current Unreal pipeline, the arena loaded with its gameplay intact. Enemies spawned, the fight ran and the old project had survived without altering the original. That was the moment arena modding stopped being a theory again.

Turning the proof into something everyone could use

A collection of one-off scripts would have solved the problem for one machine. ArenaKit turned the discovery into the same sort of visual workflow as Limelight: find the correct editor, create or patch an arena, build it, check it and put it on stage.

  • A proper starter: Player Start, enemy navigation and spawn space, boundaries, launch protection, fall protection and preview lighting are already in place.
  • A current build route: ArenaKit uses the Epic Games Launcher version of Unreal Engine 5.7 instead of demanding a 300–400 GB source build or an Epic-linked GitHub account.
  • A Legacy Patcher: older editable arena projects are copied into ArenaKit, repaired and rebuilt while the originals remain untouched.
  • A complete package: the app cooks, validates and creates the matching .pak, .utoc, .ucas, ArenaKit JSON and shareable ZIP.

ArenaKit became the newest member of the family because it followed the same rule as everything before it: hide the awkward technical work without hiding what the tool is actually doing. The first public release, v0.1.0, went live on the same day.

Whatever Joins the Family Next

Limelight grew because each solved problem revealed a more interesting one behind it. A mod organiser needed launch modes. Runtime switching needed a native bridge. A reliable Live Loader made X19 possible. Local co-op and remote input eventually gave Chuckles a way onto another PC. When arena modding stopped working, ArenaKit carried the family back into Unreal authoring.

The next steps are broader replacement support, a more resilient Live Loader, continued ArenaKit compatibility, localisation, continued LimelightMP experiments and whatever questionable idea wanders backstage next.
